# Milestone 5 greybox building contract

The supported greybox playtest gate passed on 2026-09-29; see `MILESTONES.md` for results and limitations. Use `L_M5Building`, with its small extension of the M4 test arena. No saved map changes occur during gameplay building.

The current native defaults used by `DA_BuildingCatalog` define eight stable piece IDs, names, Gameplay Tags, wood costs and health. Foundation, wall, floor, roof/ceiling, door-with-frame, chest, window wall and exterior stairs use engine cubes. Existing six IDs/enum values are preserved; Window/Stairs append. Initial pieces cost two wood and have100health; these are test values. Dimensions and compatible support rules are deliberately fixed for this structural grid.

Foundation centers snap to a 400 cm world grid on flat ground, checked at center and four corners. Walls/doors snap to a platform edge at 90-degree rotations; floor/ceiling pieces snap above a supported wall or door. Storage snaps to a 100 cm grid on a platform. Clients send a piece ID and quarter turn only; the server derives the actual target from the possessed living pawn's view. It rechecks reach, ownership, collision (including players), support, catalog, resource cost and a 128-piece development limit before spawning and consuming wood. The local green/red wireframe is advisory; the server decides placement.

Structures replicate definition, kind, health, owning PlayerState and support. Ownership survives pawn respawn; reconnect ownership/save restoration remains M8. Owner-only door access is the initial permission rule. Group permissions are deferred. A closed primitive door blocks movement; opening hides the panel while retaining the frame. J applies a validated 25-damage owner hammer action. H removes an owned targeted piece without refund. Supporting pieces and nonempty storage reject demolition and lethal damage, preventing unsupported pieces or silent item loss; remove children and empty storage first. This is a cooperative greybox policy, not final PvP damage rules.

Storage reuses the inventory component, eight slots / 60 weight, with owner-only replicated contents. E opens targeted owned storage. Transfers require continued reach and clear view, preserve exact food deadlines, validate capacity and quantities and commit only after destination acceptance. U deposits one selected bag item; O withdraws one from the first stored stack. Failed/replayed transfers cannot duplicate items. Food ages normally in storage; no refrigeration or freshness reset is implied. Later preservation can build on the existing deadline contract.

Current controls: B opens the explicit eight-piece picker; click/1–8 selects and returns to first-person preview, T rotates, left click places. B exits preview; B again reopens the picker. N remains an optional cycle shortcut while placing. E opens an aimed-at owned chest window with Store/Take1/stack, Sort, Quick Store and chest item-filter settings; E/Tab/Close returns to first person. H/J remain owned demolition/developer damage during placement. Windows support Floor/Roof, exterior stairs attach to platforms and reach the next storey without intersecting the solid upper slab. Keep the flight's edge clear of walls. Legacy U/O bindings remain but the visible GUI is the normal storage path. See BUILDING_MENUS_M11.md and G2 in TRELLO_TEST_GUIDES.md for current evidence and exact controls; older M5 shortcut descriptions above are historical.

Developer commands: `PF.TestBuildingPlacement` inspects existing runtime structure integrity; it fails if none exist and does not claim functional placement coverage. `PF.ResetBuildings` removes only the sole player's empty runtime pieces in `L_M5Building`, with no refund or saved map mutation. Client calls are rejected. Functional tests are `PF.Building.PlacementAndStorage` and opt-in `PF.Building.Live` with `-PFRunBuildingLiveTests -PFExpectedPlayers=1|2`.

Rendered testing is uncapped at the user's request: session-only `t.MaxFPS 0`, `r.VSync 0` and `bSmoothFrameRate=False`, with graphics quality unchanged. Report resolution, frame-time sample and memory; FPS from this tiny arena is not an open-world optimization claim. NullRHI tests verify gameplay/network behavior, not rendering performance.
